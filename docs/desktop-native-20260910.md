## 打开恢复

原界面只等待 `OpenFLV` 返回。宿主若已接纳文件而响应丢失，界面没有
session ID，却又被宿主的单会话槽位挡住，无法关闭或恢复该文件。

现在每次打开带有递增的十进制 uint64 请求 ID。宿主只保存最新请求的
待完成/完成结果；同 ID 去重，旧 ID 拒绝。`GetOpenResult` 返回当前结果，
包括最新会话状态和文件名，不重新打开文件或选择器。若原请求尚未送达，
确认会先封存该 ID 为已取消，再返回；迟到的原命令因此不能创建孤立会话。

打开响应报错或 5 秒内不返回时，界面进入“正在确认打开结果…”，按
200 ms 间隔串行确认。选择器仍打开则继续等候，已接纳则恢复原会话。
确认调用本身也有 5 秒超时：失败后停止自动查询，保留“重试查询”入口，
重试只查询原 ID。迟到结果不能覆盖已恢复或新打开的文件。销毁控制器
时清理本地定时器，文件清理由宿主负责。

更新了真实 Wails 生成绑定并修订 ADR-011。根模块、六方法桌面适配层
v1、CLI/JSON 合同和依赖版本均未改变；没有加入详情解析等新功能。

## 受控 I/O 下的取消与退出

本机百万 Tag 扫描在自动点击的工具往返前就结束；增加样本体积、启用
race 和对临时样本做 LZX 压缩仍未提供稳定操作窗口。这些已结束的扫描
没有记作取消通过。

为稳定验证生命周期，另建 `MuxRay-io-acceptance.exe`：Go `-overlay`
仅覆盖 scratch 中的 `internal/session/session.go` 构建输入，对一个
49,722-byte 真实 FLV 的 `ReadAt` 加门控。第 23 次读取前暂停，此前已
提交 10 个 Tags；手动创建 release 标记才恢复实际读取。前端、Wails
IPC、宿主、扫描算法和上下文取消逻辑仍使用本批代码，生产源码及
`MuxRay.exe` 没有加入该门控。其他路径的文件不受门控影响。

实际通过的原生操作：

1. 选择样本并确认 entered 标记，界面保持“扫描中”。点击真实的
   “取消扫描”按钮后变为“正在取消”，没有提前宣称扫描完成。
2. 释放读取后变为“已取消”，显示 5,371 bytes、10 Tags、0 诊断，
   部分结果页为 ID 0–9，页脚为“本页 10 条 · 共 10 条”。Close
   标记记录无错误，文件可独占读取。关闭文件后正常恢复空态并重开。
3. 再次打开并暂停，保持 gate 未释放，按 Alt+F4 关闭真实窗口。
   独立进程观察记录从发送输入到进程退出约 3.0 秒，退出码为 0。
   此时没有 orderly Close 标记；这是退出超时后 OS 回收资源，不能
   记为阻塞读取被打断或正常源关闭。退出后文件可独占读取。

此检查证明真实窗口/IPC 的取消、部分结果保留和有界退出路径；它不等同
于在未修改的生产二进制上遇到自然慢盘。源码覆盖、构建记录、门控脚本
和无 GUI 校验脚本保留在本地 scratch，独立 EXE 不用于发行。
